# SDK-011 Functional Requirements

## 02.01 Knowledge Ingestion

### 1. Purpose

This document defines the functional requirements for bringing source content into the RetailBrainAI Knowledge & Context Framework. Ingestion begins when a source or knowledge item is submitted, detected, or synchronized and ends when a canonical ingestion record has been accepted for downstream processing or has reached a terminal rejected state.

This document does not define parsing, chunking, embedding, indexing, retrieval, or context assembly behavior except where ingestion must provide inputs or guarantees to those stages.

### 2. Scope

The ingestion capability must support:

- source registration and configuration;
- push, pull, batch, and event-driven ingestion;
- source identity and version tracking;
- tenant and authorization context capture;
- content and metadata validation;
- idempotency and duplicate detection;
- ingestion orchestration and status tracking;
- quarantine and rejection handling;
- retry, replay, and cancellation;
- lifecycle-triggered updates and deletions;
- operational controls and observability;
- extension through provider-neutral connector contracts.

### 3. Core Actors

| Actor | Responsibility |
|---|---|
| Knowledge administrator | Registers sources, configures policies, initiates administrative operations, and reviews failures. |
| Source connector | Discovers or receives source changes and submits ingestion requests. |
| Producing application | Pushes a knowledge item or change directly through an API or event contract. |
| Ingestion orchestrator | Validates requests, enforces idempotency, persists state, and dispatches downstream work. |
| Security services | Supply tenant, principal, authorization, classification, and policy decisions. |
| Operations user | Monitors ingestion health, retries eligible failures, and manages quarantined items. |
| Downstream processor | Consumes accepted ingestion jobs for parsing, normalization, enrichment, and representation generation. |

### 4. Canonical Concepts

#### 4.1 Knowledge source

A registered origin from which one or more knowledge items are ingested. A source has a stable identifier, owner, tenant scope, connector type, configuration reference, security classification, synchronization mode, lifecycle state, and processing policy.

#### 4.2 Source item

A uniquely identifiable item within a source, such as a file, database record, API resource, report, product record, article, or event-backed entity.

#### 4.3 Source version

A source-provided or framework-derived identifier representing a specific state of a source item. Examples include an ETag, object version, commit SHA, row version, last-modified timestamp plus content hash, or domain revision number.

#### 4.4 Ingestion request

A command to create, update, reprocess, deactivate, or delete a knowledge item.

#### 4.5 Ingestion job

A durable framework record representing execution of an ingestion request through validation and handoff to downstream processing.

#### 4.6 Canonical ingestion envelope

The provider-neutral payload accepted by the framework. It contains identity, source, tenant, operation, content reference or inline content, metadata, security attributes, version information, trace context, and idempotency data.

### 5. Ingestion Modes

The framework shall support the following modes through a common canonical contract.

#### 5.1 Push ingestion

A producing application submits content or a content reference directly through a synchronous API. The API acknowledges acceptance or rejection but does not wait for expensive downstream processing.

#### 5.2 Pull ingestion

A registered connector enumerates source items and submits detected changes. Connector checkpoints must be durable and independent of individual item-processing state.

#### 5.3 Batch ingestion

An authorized actor submits a manifest containing multiple source items or content references. Each item must receive its own ingestion identity and terminal status, while the batch exposes aggregate progress.

#### 5.4 Event-driven ingestion

A source or integration service emits a change event that is converted into a canonical ingestion request. Event redelivery must be safe.

#### 5.5 Administrative ingestion

An authorized administrator may trigger source synchronization, item reprocessing, version replay, deletion, or quarantine release.

### 6. Functional Requirements

Requirement identifiers are stable and must be used in implementation plans, tests, and acceptance evidence.

#### 6.1 Source registration and management

**FR-ING-001 — Register a source**  
The framework shall allow an authorized caller to register a knowledge source with a globally unique framework identifier and a tenant-scoped human-readable name.

**FR-ING-002 — Source ownership**  
Each source shall identify a business owner and technical owner using resolvable principal or group references.

**FR-ING-003 — Connector type**  
Each source shall declare a connector type from a registered connector catalogue. Unknown or disabled connector types shall be rejected.

**FR-ING-004 — Configuration isolation**  
Connector configuration shall be stored or referenced separately from the source's public metadata. Secret values shall be represented only by approved secret references and shall never be returned through standard read APIs.

**FR-ING-005 — Synchronization mode**  
A source shall declare one or more supported ingestion modes: push, pull, batch, event-driven, or administrative.

**FR-ING-006 — Source lifecycle**  
A source shall support the states `DRAFT`, `ACTIVE`, `PAUSED`, `DISABLED`, and `DECOMMISSIONED`. Only active sources may initiate normal ingestion.

**FR-ING-007 — Processing policy assignment**  
A source shall reference a versioned processing policy that defines allowed content types, size limits, classification rules, downstream pipeline selection, retention, and failure behavior.

**FR-ING-008 — Source validation**  
Activation shall require successful configuration validation and, where supported, a connector connectivity test.

**FR-ING-009 — Source updates**  
Updates to source configuration shall be versioned and auditable. Changes affecting identity, security, or processing shall not silently alter previously ingested item history.

**FR-ING-010 — Source pause**  
Pausing a source shall prevent new scheduled or pull ingestion while preserving existing records and allowing already accepted jobs to follow configured cancellation policy.

#### 6.2 Request acceptance

**FR-ING-011 — Canonical envelope**  
All ingestion entry points shall map inputs into the same canonical ingestion envelope before validation.

**FR-ING-012 — Required identity fields**  
Every request shall include tenant identifier, source identifier, source item identifier, operation, and idempotency key or sufficient fields for deterministic idempotency derivation.

**FR-ING-013 — Supported operations**  
The framework shall support `CREATE_OR_UPDATE`, `REPROCESS`, `DEACTIVATE`, `DELETE`, and `RESTORE` where permitted by policy.

**FR-ING-014 — Inline and referenced content**  
A create or update request may contain approved inline content or a resolvable content reference. The framework shall reject requests containing both unless a connector-specific policy explicitly defines precedence.

**FR-ING-015 — Accepted acknowledgement**  
On successful acceptance, the framework shall return an ingestion job identifier, normalized item identifier, acceptance timestamp, current state, and correlation identifier.

**FR-ING-016 — Asynchronous processing**  
Acceptance shall not imply successful parsing, indexing, or retrieval availability. The response and event contracts shall distinguish `ACCEPTED` from downstream completion.

**FR-ING-017 — Request size enforcement**  
The API shall reject requests that exceed configured inline payload or metadata limits before durable job creation unless streaming ingestion is explicitly supported.

**FR-ING-018 — Content type allow-list**  
The request shall be rejected or quarantined when the declared or detected content type is not permitted by the source policy.

**FR-ING-019 — Correlation propagation**  
The framework shall accept and propagate approved correlation, causation, and trace identifiers through all ingestion stages.

**FR-ING-020 — Caller context**  
The framework shall record the authenticated caller, effective tenant, delegated identity where applicable, and originating application for each request.

#### 6.3 Identity, versioning, and idempotency

**FR-ING-021 — Stable item identity**  
The canonical knowledge item identity shall be derived from tenant, source, and source item identifier and shall remain stable across versions.

**FR-ING-022 — Source version capture**  
The framework shall record the source version supplied by the connector or producer. When unavailable, the framework shall derive a version fingerprint from approved immutable attributes and content hash.

**FR-ING-023 — Content hash**  
For accessible content, the framework shall compute or verify a cryptographic content hash using a configurable approved algorithm.

**FR-ING-024 — Idempotent acceptance**  
Repeated requests with the same tenant, source, operation scope, and idempotency key shall not create duplicate logical jobs within the configured idempotency window.

**FR-ING-025 — Idempotent response**  
A repeated idempotent request shall return the original or current job identity and status unless the original request is no longer retained under policy.

**FR-ING-026 — Idempotency conflict**  
If an idempotency key is reused with materially different request content, the framework shall reject the request with a stable conflict error.

**FR-ING-027 — Duplicate version suppression**  
A create or update request for a source version already successfully accepted shall be treated as no-op, replay, or explicit reprocessing according to operation and policy.

**FR-ING-028 — Out-of-order versions**  
The framework shall detect older source versions arriving after newer versions when the source provides comparable ordering semantics. Policy shall determine whether to reject, retain as history, or process without promoting it as current.

**FR-ING-029 — Concurrent update serialization**  
Conflicting lifecycle operations for the same logical item shall be serialized or resolved using optimistic concurrency and deterministic precedence rules.

**FR-ING-030 — Version history**  
Ingestion history shall retain the relationship between each job, logical item, source version, and resulting downstream artifact version.

#### 6.4 Validation

**FR-ING-031 — Schema validation**  
The canonical envelope and metadata shall be validated against a versioned schema before acceptance.

**FR-ING-032 — Tenant validation**  
The effective tenant shall be valid, active, and authorized for the registered source.

**FR-ING-033 — Source validation**  
The source shall exist, belong to the effective tenant or an explicitly governed shared scope, and permit the requested operation.

**FR-ING-034 — Item identifier validation**  
Source item identifiers shall conform to connector and platform length, character, normalization, and uniqueness constraints.

**FR-ING-035 — Metadata validation**  
Metadata shall be checked for allowed keys, types, sizes, reserved namespaces, and classification rules.

**FR-ING-036 — Reference validation**  
Content references shall use approved schemes and locations and must not permit server-side request forgery, unrestricted network access, or path traversal.

**FR-ING-037 — Integrity validation**  
When a producer supplies content length, hash, signature, or checksum, the framework shall verify it before downstream processing where technically possible.

**FR-ING-038 — Malware and active-content screening**  
Content types subject to security scanning shall not proceed to normal processing until the configured screening result is successful.

**FR-ING-039 — Classification validation**  
The requested security classification may be elevated by policy or automated detection but shall not be reduced below source or tenant policy without an authorized override.

**FR-ING-040 — Validation failure detail**  
Validation failures shall return stable error codes and safe field-level detail without exposing secrets, internal paths, or provider credentials.

#### 6.5 Metadata and security attributes

**FR-ING-041 — Canonical metadata**  
The framework shall capture a minimum canonical metadata set including title where available, source URI or source reference, language where known, content type, source timestamps, ownership, classification, tags, and lifecycle attributes.

**FR-ING-042 — Extensible metadata**  
Domain-specific metadata shall be supported through namespaced schemas governed by registration and versioning rules.

**FR-ING-043 — Access-control attributes**  
Each item shall carry or reference the attributes required to evaluate access during retrieval, including tenant, visibility scope, principal or group grants, policy references, and source-specific restrictions.

**FR-ING-044 — Security inheritance**  
An item shall inherit mandatory source-level and tenant-level restrictions. Item-level metadata may further restrict access but shall not broaden it beyond the source policy unless explicitly authorized.

**FR-ING-045 — Metadata provenance**  
The framework shall distinguish source-provided, connector-derived, system-derived, administrator-supplied, and model-derived metadata.

**FR-ING-046 — Timestamp preservation**  
Source creation, source modification, discovery, ingestion acceptance, and processing timestamps shall be stored separately and shall not overwrite one another.

**FR-ING-047 — Sensitive metadata handling**  
Sensitive metadata shall be encrypted or tokenized according to classification policy and excluded from logs and metrics.

#### 6.6 Orchestration and state management

**FR-ING-048 — Durable job state**  
Every accepted request shall create or resolve to a durable ingestion job record before downstream work is dispatched.

**FR-ING-049 — State model**  
The ingestion job shall support at least `RECEIVED`, `VALIDATING`, `ACCEPTED`, `QUEUED`, `PROCESSING`, `SUCCEEDED`, `SUCCEEDED_WITH_WARNINGS`, `REJECTED`, `QUARANTINED`, `FAILED_RETRYABLE`, `FAILED_TERMINAL`, `CANCELLING`, and `CANCELLED`.

**FR-ING-050 — Valid state transitions**  
State transitions shall be enforced by a versioned state machine. Invalid transitions shall fail with a stable framework error.

**FR-ING-051 — Atomic acceptance and dispatch**  
Persistence of accepted state and publication of downstream work shall use an outbox, transactional messaging, or equivalent pattern preventing accepted jobs from being silently lost.

**FR-ING-052 — Progress visibility**  
The job shall expose current stage, attempt count, last transition time, safe progress detail, and terminal result summary.

**FR-ING-053 — Batch aggregation**  
Batch ingestion shall expose counts for pending, accepted, succeeded, warning, rejected, quarantined, failed, cancelled, and total items.

**FR-ING-054 — Partial batch success**  
Failure of one batch item shall not roll back unrelated accepted items unless the caller explicitly requested an atomic batch and the implementation supports it.

**FR-ING-055 — Downstream handoff contract**  
Accepted work shall include canonical identity, content location, metadata, security attributes, source and policy versions, trace context, and expected operation.

**FR-ING-056 — Completion correlation**  
Downstream completion or failure events shall correlate to the ingestion job and logical item without relying on provider-specific identifiers.

#### 6.7 Pull synchronization and checkpoints

**FR-ING-057 — Connector checkpoint**  
Pull connectors shall persist a durable checkpoint representing the last safely enumerated source position.

**FR-ING-058 — Checkpoint advancement**  
A connector shall advance its checkpoint only according to its declared delivery semantics. At-least-once discovery is acceptable when item ingestion remains idempotent.

**FR-ING-059 — Full and incremental synchronization**  
Connectors shall declare whether they support full scan, incremental scan, or both.

**FR-ING-060 — Pagination safety**  
Connector pagination tokens and cursors shall be treated as opaque, protected values and shall not be exposed in normal logs.

**FR-ING-061 — Change detection**  
Connectors shall map source additions, updates, deletions, moves, and permission changes into canonical operations where the source exposes those changes.

**FR-ING-062 — Missing item reconciliation**  
Full synchronization shall support policy-driven detection of items no longer present in the source without immediately deleting knowledge based on a single incomplete scan.

**FR-ING-063 — Connector throttling**  
Connectors shall respect source rate limits and framework backpressure signals.

**FR-ING-064 — Connector lease**  
Only one active worker or coordinated worker group shall own a non-partitionable source synchronization lease at a time.

#### 6.8 Retry, replay, cancellation, and quarantine

**FR-ING-065 — Retry classification**  
Failures shall be classified as retryable, terminal, quarantinable, or policy-blocked using SDK-004 error semantics.

**FR-ING-066 — Automated retry**  
Retryable failures shall use configurable bounded exponential backoff with jitter and maximum attempts or elapsed duration.

**FR-ING-067 — Retry idempotency**  
Retries shall reuse the logical job and operation identity and shall not create duplicate source versions or downstream artifacts.

**FR-ING-068 — Manual retry**  
Authorized operations users shall be able to retry eligible failed jobs while recording actor, reason, and selected restart stage.

**FR-ING-069 — Replay**  
Authorized users or services shall be able to replay a retained source version through a newer processing policy without altering the original ingestion history.

**FR-ING-070 — Cancellation request**  
Authorized callers may request cancellation of queued or active jobs. Cancellation shall be best effort once external or downstream work has begun.

**FR-ING-071 — Quarantine**  
Suspicious, policy-ambiguous, malformed, or security-blocked content may be quarantined rather than permanently rejected.

**FR-ING-072 — Quarantine isolation**  
Quarantined content shall be isolated from normal processing, search, retrieval, and context assembly.

**FR-ING-073 — Quarantine review**  
Authorized reviewers shall be able to inspect safe metadata, record a decision and reason, release the item, or reject it permanently.

**FR-ING-074 — Dead-letter handling**  
Messages that exceed retry policy shall be moved to a governed dead-letter mechanism with preserved correlation and diagnostic context.

#### 6.9 Update, deactivation, deletion, and restoration

**FR-ING-075 — Update ingestion**  
A newer accepted source version shall create a new immutable version while retaining the logical item identity.

**FR-ING-076 — Current version promotion**  
Only a successfully processed eligible version may become the current retrievable version unless policy allows provisional visibility.

**FR-ING-077 — Permission-only update**  
A source permission change shall be ingestible without requiring content change and shall trigger propagation to all retrieval representations and caches.

**FR-ING-078 — Deactivation**  
Deactivation shall make the item ineligible for normal retrieval while preserving content and history according to retention policy.

**FR-ING-079 — Deletion request**  
Deletion shall create a durable lifecycle job and remove or tombstone all governed representations, indexes, caches, and derived artifacts according to policy.

**FR-ING-080 — Delete precedence**  
A confirmed deletion shall take precedence over queued create, update, reprocessing, or restoration work for the same item unless a legal hold or authorized recovery workflow applies.

**FR-ING-081 — Legal hold**  
The framework shall block destructive deletion when an applicable legal or compliance hold exists and shall return a policy-specific result.

**FR-ING-082 — Tombstones**  
The framework shall retain sufficient tombstone data to prevent accidental resurrection from delayed events while respecting data-minimization policy.

**FR-ING-083 — Restoration**  
Restoration shall require an eligible retained version, explicit authorization, and a new lifecycle event. Restoration shall never erase the prior deletion or deactivation history.

#### 6.10 Status and administration APIs

**FR-ING-084 — Job lookup**  
Authorized callers shall be able to retrieve a job by ingestion job identifier.

**FR-ING-085 — Item history**  
Authorized callers shall be able to list ingestion jobs and versions for a logical item.

**FR-ING-086 — Filtered job search**  
Operations APIs shall support bounded filtering by tenant, source, state, operation, time range, correlation identifier, and failure code.

**FR-ING-087 — Pagination**  
List operations shall use stable cursor-based pagination and deterministic ordering.

**FR-ING-088 — Safe diagnostics**  
Administrative responses shall expose actionable diagnostics while redacting secrets, sensitive content, and unauthorized metadata.

**FR-ING-089 — Source synchronization trigger**  
Authorized callers shall be able to start a source synchronization and receive a synchronization-run identifier.

**FR-ING-090 — Synchronization status**  
The framework shall expose checkpoint, start and completion times, aggregate counts, current state, and failure summary for synchronization runs.

#### 6.11 Events

**FR-ING-091 — Lifecycle events**  
The framework shall publish versioned events for source activation changes, job acceptance, quarantine, terminal success, warning, failure, cancellation, item deactivation, deletion, and restoration.

**FR-ING-092 — Event envelope**  
Events shall use SDK-005 contracts and include event identifier, event type, schema version, tenant, aggregate identity, correlation, causation, occurrence time, producer, and safe payload.

**FR-ING-093 — No sensitive content in events**  
Events shall reference content and protected diagnostics rather than embedding sensitive source content unless an explicit secure-event contract permits it.

**FR-ING-094 — Event delivery semantics**  
Consumers shall assume at-least-once delivery and use event identifiers and aggregate versions for deduplication.

**FR-ING-095 — Ordering metadata**  
Events for the same logical item shall include a monotonic aggregate or lifecycle version where feasible so consumers can detect stale delivery.

#### 6.12 Observability and auditability

**FR-ING-096 — Structured logging**  
All stages shall emit SDK-003 compliant structured logs with tenant-safe correlation fields and without raw content by default.

**FR-ING-097 — Metrics**  
The framework shall expose request rate, acceptance rate, item volume, byte volume, validation failures, duplicate suppression, processing latency, queue delay, retry count, quarantine count, terminal failures, and synchronization lag.

**FR-ING-098 — Distributed tracing**  
Trace context shall span API acceptance, persistence, message publication, connector activity, and downstream handoff.

**FR-ING-099 — Audit record**  
Administrative and security-sensitive operations shall generate immutable audit information including actor, action, target, time, reason, result, and correlation.

**FR-ING-100 — Content logging prohibition**  
Raw source content, credentials, access tokens, and unrestricted metadata shall not be emitted to application logs, traces, or metric labels.

### 7. API-Level Behavioral Requirements

#### 7.1 Create or update request

A canonical request should be representable as:

```json
{
  "schemaVersion": "1.0",
  "tenantId": "tenant-123",
  "sourceId": "source-456",
  "sourceItemId": "products/sku-10001",
  "operation": "CREATE_OR_UPDATE",
  "sourceVersion": "42",
  "idempotencyKey": "source-456:products/sku-10001:42",
  "content": {
    "reference": "object://knowledge-ingress/tenant-123/item-789",
    "contentType": "application/pdf",
    "length": 248901,
    "sha256": "<hex-digest>"
  },
  "metadata": {
    "title": "Store Operations Manual",
    "language": "en-GB",
    "sourceModifiedAt": "2026-07-29T15:44:12Z",
    "tags": ["operations", "stores"]
  },
  "security": {
    "classification": "INTERNAL",
    "visibilityScope": "GROUP_RESTRICTED",
    "policyRefs": ["policy-retail-ops-readers-v3"]
  },
  "trace": {
    "correlationId": "<uuid>",
    "causationId": "<uuid>"
  }
}
```

This example is illustrative. The authoritative schema will be defined in the API-contract document.

#### 7.2 Acceptance response

```json
{
  "jobId": "ing-01J...",
  "knowledgeItemId": "ki-01J...",
  "state": "ACCEPTED",
  "acceptedAt": "2026-07-30T10:45:00Z",
  "correlationId": "<uuid>",
  "duplicate": false
}
```

#### 7.3 Error response

Errors shall use SDK-004 and include a stable code, safe message, correlation identifier, retryability, and optional field violations. Provider-specific exception text shall not cross the framework boundary.

### 8. Authorization Requirements

The ingestion capability shall distinguish at least these permissions:

- source registration;
- source activation and configuration update;
- item submission;
- batch submission;
- synchronization trigger;
- job read;
- content diagnostic access;
- retry;
- cancellation;
- quarantine review;
- delete;
- restore;
- cross-tenant shared-scope administration.

Authorization shall be evaluated against the effective tenant and target source. Possession of a job or item identifier shall never be sufficient authorization.

### 9. Configuration Requirements

The framework shall make the following settings configurable at appropriate platform, tenant, source, and connector scopes:

- accepted content types;
- maximum inline and referenced content size;
- metadata limits;
- idempotency retention;
- retry policy;
- quarantine policy;
- connector concurrency;
- source rate limits;
- batch limits;
- synchronization schedule reference;
- checkpoint retention;
- malware scanning requirement;
- hashing algorithm;
- timeout values;
- retention and tombstone duration;
- event publication behavior;
- logging and diagnostic verbosity.

Lower scopes may further restrict platform policy but shall not weaken mandatory security controls.

### 10. Failure Semantics

The implementation shall provide stable categories for:

- invalid request;
- unauthorized or forbidden operation;
- source not found or inactive;
- unsupported connector or operation;
- duplicate request;
- idempotency conflict;
- unsupported content type;
- content too large;
- content reference unavailable;
- integrity check failure;
- security scan failure;
- policy violation;
- concurrency conflict;
- upstream throttling;
- temporary source failure;
- messaging or persistence failure;
- retry exhaustion;
- cancellation;
- legal-hold conflict.

Every error category shall define retryability, HTTP mapping where applicable, message-handling behavior, logging level, and audit requirements.

### 11. Acceptance Criteria

Knowledge ingestion is acceptable for implementation completion when all of the following are demonstrated:

1. A source can be registered, validated, activated, paused, and decommissioned with authorization enforcement.
2. Push, batch, pull, and event inputs map to one canonical ingestion envelope.
3. Duplicate event or API delivery does not create duplicate logical versions.
4. Reuse of an idempotency key with different content produces a deterministic conflict.
5. Accepted jobs survive service restart and are not lost between database persistence and message publication.
6. Tenant and source authorization is enforced for write and read operations.
7. Content references are constrained to approved schemes and do not permit arbitrary network or filesystem access.
8. Unsupported, malicious, or policy-ambiguous content is rejected or quarantined according to policy.
9. A job exposes durable status and a valid state-transition history.
10. Retry and manual replay do not corrupt version history or duplicate downstream artifacts.
11. Source permission changes can propagate without requiring a content change.
12. Delete operations create tombstones and trigger removal of derived representations.
13. Legal hold blocks destructive deletion.
14. Events are versioned, contain correlation metadata, and exclude raw sensitive content.
15. Logs, traces, and metrics contain no raw content or secrets in automated tests.
16. Connector checkpoints support safe restart and at-least-once discovery.
17. Batch ingestion reports per-item and aggregate outcomes.
18. All FR-ING requirements are traced to automated or explicitly approved manual tests.

### 12. Implementation Notes for Claude Code

Implementation should begin with the canonical domain model and state machine, followed by storage ports, API contracts, event contracts, and one reference in-memory or local adapter. Provider-specific connectors should be implemented only after contract tests prove idempotency, tenant isolation, lifecycle precedence, and safe retries.

Recommended initial package boundaries:

```text
knowledge-context/
  ingestion-domain/
  ingestion-application/
  ingestion-contracts/
  ingestion-persistence/
  ingestion-messaging/
  ingestion-api/
  connectors-spi/
  connectors-reference/
  ingestion-testkit/
```

Each adapter must pass a shared conformance suite. No connector may write directly to vector indexes or bypass the canonical job and lifecycle records.
